# Phase 11 validation - what Alethic can actually do

**Capability under test:** the platform, given real work. Phase 11 is the one
the other ten were written for, and its subject is not a feature - it is the
answer to a question: *what does Alethic do reliably, what does it do
sometimes, and what does it not do at all.*

**Definition of Done:** *there is a written answer to that question.* Written,
and computed rather than asserted - `validation/REPORT.md` is generated by
`alethic validation-report` from recorded runs, and this file is what a person
should read beside it.

## How it was run

Nine scenarios declared under `validation/scenarios/`, one per capability the
first ten phases added, each stating what is asked, what the machine must have,
and what would count as done - written before the run.

Against locally served models, no provider key and nothing spent:
`gemma4:31b-cloud` for planning, execution and synthesis, `lfm2.5:8b` for
verification and extraction (`infrastructure/llm/models.local.toml`).

```bash
export ALETHIC_MODEL_CATALOG_PATH=infrastructure/llm/models.local.toml
uv run alethic validate
uv run alethic validation-report --write validation/REPORT.md
```

Every run was **unattended**. That matters and is not a shortcut: with nobody at
the keyboard, everything the policy layer sends to a person is refused, and the
report says NEEDED_APPROVAL rather than pretending the capability is absent.
It is the honest reading of a machine with nobody watching it, and it is how a
scheduled run in Phase 12 will behave.

## What the platform does

The verdicts are in `validation/REPORT.md` and are recomputed every time. What
follows is what they mean.

**Reliable.** Reading the web with a named source, and refusing to send. Both
passed every attempt. The second one is the more interesting: an employee told
plainly to deliver a file reached for `code.run`, was refused by its own
declared policy, said so, and stopped. That is Phase 10 holding under a request
designed to push through it.

**Sometimes.** Sorting a folder, answering a question directly, writing a
summary from notes. Each has worked and each has failed, and in no case was the
work itself the problem - see the four defects below.

**Not at all, on this machine, unattended.** Computing over a CSV. `code.run`
is EXECUTE and irreversible, the analyst declares `no_irreversible_actions`, and
with no approver every attempt is refused. The capability is not missing; the
configuration that would let it run is a person at the keyboard, and the report
should not flatter that into a pass.

**Unknown.** Driving a screen. Skipped: `ALETHIC_FLAGS__COMPUTER_USE` is off
here, and a skip is recorded as a skip. A completion rate that fell when the
user switched off their desktop would be measuring configuration.

## The four defects the pass found

Each of these ran before it was a finding, and each is now either fixed or in
the plan. This is the part of the phase that is worth more than the table.

### 1. Alethic answers instead of working

*"There are meeting notes in `notes/`. Read them and leave me a file called
`notes/summary.md`."* Read as `needs_work: false`, answered in one sentence, no
task, no tool, no file - and reported DONE.

```
{"needs_work": false, "constraints": ["count", "format", "where"], "event": "alethic.intent_read"}
{"event": "alethic.answered_directly"}
```

Answering directly is a deliberate feature (§7.5) and this is its failure mode:
the judgement about whether a request needs work is made by a model, before any
work has been attempted, and when it is wrong the platform reports success
having done nothing. It is the most expensive class of defect here, because
nothing downstream can catch it - the verifier is checking an answer that was
never supposed to be an answer.

It also exposed a hole in the taxonomy. The first classification called this
EXPECTATION - *it finished and produced the wrong thing* - which points at the
answer rather than at the decision that produced it. `classify` now returns
PLANNING whenever nothing was attempted at all and the standard was not met,
whatever the platform thought of its own success.

### 2. A refusal does not stop the attempt

The analyst, told to send a file, called `code.run`; the gate refused; it called
`code.run` again. Fifteen times, until the step budget ran out.

```
15 x approval.requested -> approval.resolved REJECTED -> tool.not_approved
{"limit": "STEPS", "steps": 16, "event": "task.limit_reached"}
```

The refusal text already says *"Do not retry it; find another way or say why you
cannot"* - and a sentence in a tool result is a suggestion. A tool refused N
times in one task should stop being offered to the model. Recorded rather than
patched: it is a change to the executor's loop, and it belongs beside the other
two items now ahead of Phase 12.

Note the contrast with the same tool in the same situation one scenario earlier,
where the analyst was refused once, said so, and stopped. Both behaviours are in
the record, which is what "sometimes" means.

### 3. The cheapest model returns the prompt's own example

Twice, the objective verifier answered with the placeholder text out of
`prompts/alethic_verifier/v1.md`:

```
{"missing": ["which criterion is unmet, and how"], "event": "alethic.objective_rejected"}
```

`lfm2.5:8b` copied the example JSON instead of filling it in, and a correct
result - the summary file was written, with the right names in it - was rejected
and escalated. Phase 10's report noted a small verifier accepting an answer that
said it could not do the work; this is the same weakness in the other direction,
and now with a line number. Verification is judgement and should not be routed
to the cheapest entry in the catalog.

### 4. Capability routing picks the wrong specialist

Moving files went to the `analyst`, because it declares CODE and the planner's
task text mentioned working things out. *"What is the capital of Australia?"*
went, on one run, to the `operator` - the screen employee - which then correctly
chose the API rung and answered without a screen. A task routed imperfectly does
beat one routed nowhere, which is the design's own claim; the cost is visible
here in steps and minutes.

## Three defects in the harness itself, found the same way

Phase 11's own tooling was written before it had ever been pointed at a real
machine, and the first passes broke it in three places. Each is fixed, with a
test, and each was a way the suite could have flattered the platform.

**A file from a previous run counted as this run's output.** `triage-an-inbox`
passed its `drafts/02-meeting-move.md` check on a draft the Phase 10 validation
had left in the workspace weeks earlier - in a run whose drafting step never
finished. The harness now fingerprints every expected path before the request
and ignores anything it did not touch.

**The second attempt met the first one's output.** Run 2 of `sort-a-folder`
found `sorted/` already populated, so every `fs.move` became an overwrite -
which is HIGH, and refused unattended. The scenario failed for a reason that had
nothing to do with sorting. Scenarios can now declare `reset:`, the paths that
must not be there when the run starts; it is the only thing in the harness that
deletes, and it refuses any path that resolves outside the workspace.

**Being asked was counted as being refused.** A run whose work went through and
whose verifier then rejected it was classified NEEDED_APPROVAL, because an
approval had been requested somewhere in it. Only an actual refusal counts now -
and every refusal reaches the audit as DENIED, so nothing is lost.

A fourth was a plain crash: a workflow scenario has no `request` of its own, and
the CLI took the first line of it.

## What this changes about the roadmap (§11.6)

Defects 1, 2 and 3 go **before** Phase 12. Parallelism and multi-employee
coordination multiply exactly the failures found here in a single employee, and
Phase 12's own premise is that it starts once the single employee is dependable.
Defect 4 is material for Phase 12.2 and 12.6. The revision is written into
`development/implementation-plan.md` beside the phase it changes.

## What is worth keeping in mind about these numbers

They are one machine, one catalog, and models that are free. `gemma4:31b-cloud`
is not the model this platform would be pointed at with a key configured, and at
least defects 1 and 3 are the kind that a stronger model makes rarer without
making them impossible - which is the argument for the scenarios existing rather
than for trusting a better model.

Nothing was spent: every number in the cost column is a real zero.
