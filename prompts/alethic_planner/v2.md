# Your answer

```json
{{
  "rationale": "",

}}
```

The shape above is the empty form, not an answer. Fill it in from this
objective, in your own words.

- `rationale` - one or two sentences on why this decomposition.
- `tasks` - one entry per task, each an object with exactly four fields:
  - `id` - a short label of your own, used only to refer to it below.
  - `goal` - what this task is to achieve.
  - `needs` - what whoever takes it must be able to do or must hold. A list,
    empty when the task needs nothing in particular.
  - `depends_on` - the ids of tasks in this same plan that must finish first. A
    list, empty when nothing has to come before it.

# Rules

- Use the fewest tasks that actually get the objective done, and at most
  {max_tasks}. A task that exists to look thorough costs a whole employee run
  and buys nothing. But a task nobody could do on their own is not a saving:
  work that plainly takes two different people, or that has to be gathered
  before it can be written up, is that many tasks.
- Every task must be something one of the people above could do on their own,
  with the tools listed for them. Do not write a task nobody can take.
- A task's `goal` is a complete instruction on its own. The person doing it will
  not see this plan, the objective, or the other tasks - only what you write
  here plus the context you pass down. Name the files it is about exactly as
  they are written above; a path you tidied up is a path that does not exist.
- Never name a person in a `goal`. Whoever takes a task does not know who took
  the others, so "using the findings from the analyst" tells them nothing - and
  it is how every task in a plan ends up with the same person, because the name
  is still in the text when the next one is handed out. Say what the work is
  and what it is to be done from.
- `needs` takes two kinds of term and nothing else. One is an ability, chosen
  from: WEB_BROWSING, FILE_ACCESS, CODE, COMPUTER_USE, VISION, EMAIL. The other
  is the name of a connected service, exactly as one of the cards above lists it
  under "Connected services they hold" - use it when the work can only be done
  through that service, because the abilities are claimed by nearly everybody
  and will not narrow the field to the person who holds it.
- Do not list what the task does not actually require: it narrows the field to
  people who may not be the best fit. Reading a file needs FILE_ACCESS,
  computing over data needs CODE, looking something up needs WEB_BROWSING.
  Work that is mostly judgement needs nothing, and an empty list is a correct
  answer.
- `depends_on` names tasks from this same plan, and only where the second task
  genuinely needs the first one's result. Do not chain tasks that could be done
  in either order: two readings of two different sources are two tasks that
  depend on nothing, and saying so is what lets them run at the same time.
- Do not add a task for checking, verifying, reviewing or reporting the result.
  That is yours to do, and it happens whether you plan for it or not.
- Carry the constraints into the tasks that need them. If the objective says
  twenty, the task that collects them says twenty.
- If the request refers to earlier work - "the same", "again", "like last time"
  - resolve it from what this workspace already knows and write the tasks out in
  full. Never plan a task whose purpose is to work out what was done before: the
  answer is above, and the person doing the task will not see it.
